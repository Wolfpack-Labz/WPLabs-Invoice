Website Showing 502 or 504? How to Troubleshoot Gateway Errors

Find 502 Bad Gateway and 504 Gateway Timeout causes across CDNs, reverse proxies, app servers, DNS, TLS and upstream health checks.

Start here: what does the gateway error tell you?

A 502 Bad Gateway usually means a server acting as a gateway or proxy received an invalid response from an upstream service. A 504 Gateway Timeout means that the gateway did not receive a timely response. Both may appear when a website is behind NGINX, a load balancer, a CDN, or another reverse proxy.

Quick answer: Capture the exact URL, response code, and timestamp; determine which layer generated the error; check upstream application health and gateway logs; then investigate connectivity, DNS, certificates, and timeouts one at a time.

This guide is intended for people who administer their own site or have permission to inspect its infrastructure. If you are only visiting the site, you cannot repair its server; retry later or report the error to the owner.

Step 1: Capture the failure before changing anything

Record the request URL, time with time zone, whether the failure is constant or intermittent, and any request ID shown on the error page. Be careful not to share private URLs, cookies, session tokens, or internal hostnames publicly.

From a terminal, use curl to see only the response headers:

curl -I --max-time 15 https://example.com/

On Windows PowerShell, use curl.exe if curl is an alias. If the problem occurs only for a specific endpoint, test that endpoint with a safe read-only request when one is supported. A HEAD request might behave differently from a normal browser GET, so compare results cautiously.

Step 2: Identify the component that returned the error

Draw the actual path of the request, for example:

Browser → CDN/WAF → Load balancer → NGINX → Application → Database

Determine which layer returned the 502 or 504. A CDN-branded error can reflect a response received from your origin or a problem in the connection to the origin, depending on the service and message. For sites using Cloudflare, follow its specific 502/504 error guidance instead of treating every gateway message as the same outage.

If you can, compare the public URL with an approved internal health endpoint. Do not bypass access controls or publish an internal origin address to diagnose a public website.

Step 3: Check whether the upstream application is running

If you control the application host, inspect the service manager or container platform. For an NGINX reverse proxy serving a local HTTP application, an authorized administrator might test a private health endpoint on the host:

curl -I --max-time 5 http://127.0.0.1:3000/health

Replace the example port and path with your application's known configuration. If /health does not exist, use the supported status endpoint rather than assuming a 404 means the app is down.

Check whether the process is running, restarted recently, or exceeded resource limits. In a containerized deployment, inspect pod/container status and readiness/liveness checks. A running process is not necessarily a healthy application: database connection failures or exhausted worker pools can prevent it from returning a timely response.

Step 4: Compare reverse-proxy and application logs

On a server you administer, inspect relevant log files or your centralized logging service. A common NGINX example is:

sudo tail -n 100 /var/log/nginx/error.log

The log location may differ on managed hosting or inside containers. Match log entries to the same timestamp and request path. Useful patterns include:

  • Connection refused: The proxy tried an address/port where nothing accepted the connection.
  • Host not found: The proxy could not resolve the configured upstream hostname.
  • Upstream timed out: The service did not answer within the allowed time; check slowness and backend dependencies.
  • TLS handshake or certificate validation error: Check hostname, certificate validity, trust chain, and protocol support between proxy and origin.
  • Application returns HTTP 500: Check application logs and the underlying exception before changing proxy settings.

Do not paste entire production logs into public forums: they may contain sensitive paths, IDs, or user data.

Step 5: Verify upstream addresses, ports, and TLS settings

Review the active proxy configuration and the current deployment's service discovery. Confirm the upstream URL points to the correct host, protocol, and port. For instance, an application changed from HTTP port 3000 to HTTPS port 8443 requires a matching configuration—not just a higher timeout value.

For NGINX, an administrator can validate syntax before applying changes:

sudo nginx -t

Syntax validation does not confirm that upstream services are reachable. If it fails, do not reload the server. If it passes, test changes in staging and deploy through your normal change process. NGINX documents proxy_pass, upstream error handling, and timeouts in its proxy module reference.

Do not disable certificate verification or reduce TLS security merely to make a gateway error disappear. Fix the certificate name/trust issue or reverse-proxy settings instead.

Step 6: Look for slow queries, overload, or deployment regressions

A request that works in staging but times out in production may depend on larger datasets, restricted database connectivity, higher traffic, or a different environment variable. Compare the failing request's response time with app/database logs and relevant system metrics such as CPU, memory, connection pool utilization, and restart counts.

Ask these questions in order:

  1. Did the error begin immediately after a release, DNS change, certificate rotation, or infrastructure update?
  2. Is the failure limited to one route or application instance?
  3. Does direct application health succeed while the public gateway fails?
  4. Are there repeated long-running database operations or dependency timeouts?
  5. Is the service retrying so often that it makes an overloaded backend worse?

Rolling back a recent application change may be appropriate if you have a tested rollback procedure. Avoid restarting every component at once; it destroys useful evidence and can interrupt healthy requests.

Step 7: Verify recovery end to end

After the targeted fix, retest the originally failing path through the normal public URL and monitor it for more than one request. Look for successful responses, reasonable latency, lower error rates, and no repeating upstream warnings. If a CDN is involved, test multiple client networks or regions when your monitoring permits.

Document the root cause and prevention step—for example, a corrected port, an application readiness check, a repaired TLS chain, or an alert for exhausted worker connections. A longer proxy timeout alone is not a complete fix if the application remains slow.

Frequently asked questions

Are 502 and 504 errors caused by the visitor's internet connection?

Usually these codes indicate a failure in the gateway-to-upstream part of the request path. A visitor can retry, but the site operator generally needs to inspect server-side evidence.

Should I raise the proxy timeout to fix a 504?

Only after measuring normal application response times and identifying the slow dependency. Increasing it blindly can keep requests open longer without fixing the bottleneck.

Does restarting NGINX fix a 502?

It may appear to help temporarily, but it can also hide the cause. Check upstream health and logs first; follow an approved deployment procedure if a restart is warranted.
